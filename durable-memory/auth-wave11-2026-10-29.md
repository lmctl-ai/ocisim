## 1. Cross-Cloud Auth Comparison & OCI Specifics

| Dimension | AWS (`awssim`) | OCI (`ocisim`) |
|---|---|---|
| **HTTP Signing Scheme** | AWS SigV4 (`HMAC-SHA256` symmetric secret derived from `secretAccessKey`) | Draft-Cavage HTTP Signatures (`Authorization: Signature version="1",keyId="<tenancy>/<user>/<fingerprint>",algorithm="rsa-sha256",headers="...",signature="<base64>"`) using asymmetric 2048-bit RSA keys |
| **Body Signing Nuance** | `X-Amz-Content-Sha256` hex digest (or `UNSIGNED-PAYLOAD` on S3) | Standard JSON control-plane `POST`/`PUT` requests sign `date (request-target) host content-length content-type x-content-sha256` (Base64 SHA-256). However, Object Storage `PutObject` (`PUT /n/{ns}/b/{b}/o/{o}`) uses `SigningStrategy.EXCLUDE_BODY` in `oci-java-sdk` and `oci-cli`, signing only `date (request-target) host` so binary streams do not require pre-buffering |
| **Auth Failure Wire Shape** | `403` XML `<Error><Code>SignatureDoesNotMatch|InvalidAccessKeyId</Code>` or JSON `UnrecognizedClientException` | `401` JSON `{"code": "NotAuthenticated", "message": "The required information to complete authentication was not provided or was incorrect."}` |
| **Permission Denial Wire Shape** | `403` `AccessDenied` / `AccessDeniedException` | `403` JSON `{"code": "NotAuthorizedOrNotFound", "message": "Authorization failed or requested resource not found."}` |

## 2. Why `ocisim` Emits `403 NotAuthorizedOrNotFound` (Instead of `404`) on Policy Denial

Real OCI services return the error code `NotAuthorizedOrNotFound` with either HTTP `404` or `403` depending on whether the caller has `inspect` permission on the parent compartment/resource. In `ocisim`'s policy evaluator (`OciAuthFilter`), we emit **HTTP `403`** with `{"code": "NotAuthorizedOrNotFound", "message": "Authorization failed or requested resource not found."}` for all policy denials because:

1. **Idempotent SDK/CLI probes treat `404` as "absent/deleted"**: Both `oci-java-sdk` callers and `lmoci` treat HTTP `404` on `HeadBucket`, `HeadObject`, and `Delete*` as a normal `exists: false` or `deleted: true` outcome (exit code `0`). Emitting `404` on a permission denial would cause `lmoci os head-bucket` or `lmoci os delete-bucket` to report success (`exists: false` / `deleted: true`) when the caller was actually denied by IAM policy.
2. **Clean `BmcException` propagation**: Emitting HTTP `403` with `code="NotAuthorizedOrNotFound"` causes `oci-java-sdk` to throw `BmcException(statusCode=403, serviceCode="NotAuthorizedOrNotFound")`, which `lmoci` surfaces as a non-zero exit (`3`) with the exact OCI service code while keeping genuine resource-not-found responses at HTTP `404`.

## 3. Dual Policy Engine Support (OCI IAM Statements + JSON Statements)

`ocisim` supports both policy representations in `--auth-config`:
- **OCI IAM policy syntax**:
  - `Allow|Deny group <G[,G2]|*>|any-user to <inspect|read|use|manage> <resource-family-or-type> in tenancy|compartment <C> [where target.bucket.name = '<glob>' | request.operation = '<glob>']`
  - Implements the OCI verb hierarchy (`manage` > `use` > `read` > `inspect`). In `Allow` statements, a higher verb grants lower verbs (e.g. `read` grants `read` and `inspect`). In `Deny` statements, a verb denies that verb level and any higher/more-privileged verb (e.g. `Deny ... to manage` blocks `manage` while preserving `read` and `inspect`).
- **JSON policy syntax**:
  - `Statement[{Effect: "Allow"|"Deny", Action: "<glob>"|[...], Resource: "<glob>"|[...], Principal?: "<glob>"|[...]}]`
- **Evaluation invariants**:
  - Default-deny whenever a policy set is attached to the credential or globally configured.
  - Explicit `Deny` always overrides `Allow` across both OCI IAM statements and JSON statements.
  - Wildcard globbing (`*` and `?`) works across actions (`oci:os:Delete*`, `oci:os:Get*`), bucket names (`target.bucket.name = 'protected-*'`), and composite resource identifiers (`bucket:allowed-*/object:report-??.txt`).
